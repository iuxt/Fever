**Fever 内存扫描、压测与优化记录 — 2026-10-07**

连续更换查询时，进程 RSS 峰值下降 80.0%，渲染器堆峰值下降 99.5%。初始页面 RSS 从 520.9 降至 470.8 MiB；初始 DOM 节点从 18,617 降至 537。

已完成的优化：

- 全文搜索移至主进程，最多同时读取 4 篇笔记，仅返回匹配 ID。清空、替换查询或切换笔记库时，取消在途读取并停止调度旧任务；保持 Unicode 小写匹配和原清单顺序。
- 分类树预先构建，侧栏只挂载视口及上下各 6 行，滚动、折叠、搜索和标签切换保留导航能力。
- CodeMirror 按需加载，复用 Markdown 扩展；Markdown 渲染和组件映射缓存，避免后台刷新重复创建预览。前端入口 JS 从约 742 kB 降至 439 kB（未压缩构建文件大小）。
- 图片经 Uint8Array 传输，主进程按字节偏移直接创建 Buffer 视图，避免普通数字数组放大内存；读取前校验文件大小。文件选择器在异步操作前固定 FileList 快照，修复清空控件导致漏导入的问题。
- SVG 预览使用 Blob URL，替换或卸载时撤销；已取消的预览跳过后续导出。普通 Markdown 图片按需加载，历史弹窗关闭后释放历史正文。
- 字数统计改为逐次匹配计数，避免保留整篇笔记的单字数组；绘图不计算不显示的 Markdown 字数。

持续压测另执行了累计 200 次编辑器切换与 80 次绘图切换。最后一次 GC 后渲染器堆为 13.8 MiB，标准运行结束为 13.1 MiB；本轮未观察到堆随循环次数持续增长。

测量口径：RSS 为 `app.getAppMetrics()` 中应用各进程的 workingSetSize 之和，可能重复计算共享页；约每 100 ms 采样一次，峰值为采样值。只在阶段边界强制回收渲染器 GC，用于比较保留对象，阶段内部正常运行。RSS 包含 Chromium/GPU 的保留内存，不能直接等同于 JavaScript 活对象或系统活动监视器的单一数值。搜索依然需要扫描磁盘正文；并发限制控制在途正文数量，内存还受单篇文件大小影响。

验证结果：19 个 Node 测试、7 个 Chrome 界面测试、开发版与打包版原生 Electron 集成测试、TypeScript 检查与生产构建均通过。界面测试使用已安装的 Chrome（本机未安装 Playwright 专用 Chromium）。内存脚本默认检查：初始笔记行少于 100、搜索堆峰值增量小于 32 MiB、绘图重复切换后堆增量小于 8 MiB。
