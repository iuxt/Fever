# 性能与资源审计 — 2026-10-15

本报告为修复前基线；已确认问题的修复和复测结果见[修复记录](./fixes-2026-10-15.md)。

扫描当前工作区的 Electron 主进程、React 编辑器、文件存储、搜索、图片处理、Git 和资源清理，并在临时笔记库中复现。没有修改业务源码或现有测试，也未访问真实笔记库。

发现 7 项性能或资源问题，另有 1 项压测脚本故障。主要风险是界面线程的同步计算、保存后重复扫描、Git 面板的大量 DOM 和失败操作留下的图片。本轮有限循环中，内存压测的现有阈值通过；这不能排除长期使用或其他负载下的泄漏。

## 环境与测量口径

- Apple M1 Pro / 16 GB，macOS 27.0.1，arm64，Node.js 24.21.0，项目本地 Electron 44.5.1。
- Electron 加载生产构建 `dist/index.html`，通过真实 preload / IPC 调用存储层。
- 内存样本：2,000 篇 Markdown，其中首页很短，其余约 64 KiB；另含 200 个矩形的绘图、8 MiB 图片传输样本。两轮各 20 次编辑器循环和 8 次绘图循环。
- 读写样本：2,000 篇笔记，其中首页很短，其余各 64 KiB；在主进程包装 `fs.readFile` / `fs.writeFile` 和存储方法，计数调用及逻辑字节量。临时路径按 realpath 后仍能匹配的特征识别。
- 逻辑读取量不等于物理磁盘读取量；操作系统文件缓存会减少实际磁盘 I/O。未使用冷缓存或系统块设备计数，Git 子进程内部 I/O 也不计入文件包装器。
- RSS 是 `app.getAppMetrics()` 各进程 workingSetSize 的和，可能重复计算共享页；每约 100 ms 采样。阶段边界强制回收渲染器 GC，不能据此推断自然 GC 时的常驻量。
- CPU 微基准使用项目实际安装的 `lowlight` / `diff`，执行与界面相同的函数，单轮样本；数字不包含 React 渲染，不是完整交互延迟。

## 已确认的问题

### 1. P1：历史 diff 在界面线程同步计算，普通大小文本也能长时间阻塞

位置：[src/RevisionDiff.tsx:6](../../src/RevisionDiff.tsx#L6)，逐行完整渲染位于第 10–17 行。

`diffLines(previousContent, content)` 在组件渲染时同步执行，没有时间、编辑距离或规模上限。两份内容完全改写、各 6,000 行的样本，合计只有约 133 KiB，单次计算耗时 **3,695.5 ms**；各 3,000 行为 919.8 ms，各 1,000 行为 103.3 ms。`useMemo` 只能缓存同一输入，不能避免首次打开版本时阻塞输入、滚动和按钮响应。结果还会一次性创建所有行的 DOM。

建议：将计算移到可取消的 Worker，设置耗时或编辑距离上限，超限时回退到受控的内容预览；对结果分页或使用虚拟列表。直接跳过相同内容可节省部分场景，但不能解决大量改写的退化。

### 2. P2：大文件在大小校验前完整读入，内存限制未覆盖读取入口

位置：[electron/vault.cjs:284](../../electron/vault.cjs#L284)；普通读取位于第 205–209 行，搜索读取位于第 84 行。

`importFile()` 先 `readFile(..., 'utf8')`，再检查 10 MB 上限。实测导入 64 MiB 临时文件时，**完整读取 64 MiB 后才拒绝**，测试 Node 进程 RSS 从 **17.6 MiB 升至 164.5 MiB**。这不是 Electron 的绝对内存预测，但证明限制不能阻止该次分配。

`read()` 和全文搜索也没有单文件大小上限。由外部程序放入库中的超大正文可以绕过保存与导入的限制；搜索限制了 4 个并发任务，却没有限制同时持有的字节数，还会生成小写副本。

建议：导入、正文读取和搜索都先验证文件大小；对可接受的大文件采用有字节上限的读取或专门预览。仅 `stat` 仍有文件在读取途中增长的可能，严格资源上限应在实际读取时继续限制字节数。分块搜索需要保留 Unicode 匹配与跨块匹配语义。

### 3. P2：搜索状态下，每次自动保存重新扫描整个笔记库

位置：[src/App.tsx:166](../../src/App.tsx#L166)、[src/App.tsx:232](../../src/App.tsx#L232)，实际扫描位于 [electron/vault.cjs:77](../../electron/vault.cjs#L77)。

保存会替换 `vault` 并递增 `searchVersion`，两者都是搜索 effect 的依赖。即使只修改一篇短笔记，也会重新读取其他所有正文。

复现：保持 `active-token` 搜索，编辑首页三次，每次等待 1.8 秒让自动保存完成：

| 场景 | 保存次数 | 新搜索次数 | 正文读取次数 | 逻辑读取量 | 主进程 CPU 时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 搜索框有内容 | 3 | 3 | 5,997 | 374.8 MiB | 1,329.2 ms |
| 搜索框为空 | 3 | 0 | 0 | 0 | 114.9 ms |

两个阶段均约 5.55 秒，CPU 时间只包含 Electron 主进程，不包含 Git 和渲染器。这里需要保持搜索结果跟随编辑更新，但不必每次重读未变化的文件。

建议：按文件版本或 mtime 缓存匹配结果，仅对保存的笔记更新当前查询结果；结构变更和外部文件变更再做失效处理。已有取消逻辑和并发限制应继续保留。

### 4. P2：批量导图中途失败，已经写入的图片没有正文引用

位置：[src/App.tsx:458](../../src/App.tsx#L458)，图片落盘位于 [electron/vault.cjs:292](../../electron/vault.cjs#L292)。

`addImages()` 逐张落盘，所有图片都成功后才插入累计 Markdown。后续图片格式不支持、超限或写入失败时，前面成功的图片没有回滚，也没有插入引用。

实测同时拖入 1 MiB 的有效 PNG 和一个 `.txt` 文件：应用提示第二个文件格式不支持，**笔记正文保持原样，但 images/ 下留下 1 MiB 的 PNG**。这些文件还会被全量暂存或自动备份纳入 Git / LFS，重复失败会增加磁盘占用。

建议：写入前先校验整批文件的格式和大小；写入期间跟踪本次新文件，失败时回滚，或明确提交已成功的图片引用。也需处理插入正文或最终保存失败的路径。

### 5. P2：Git 变更列表未虚拟化，每次刷新会处理所有行

位置：[src/GitChanges.tsx:24](../../src/GitChanges.tsx#L24)。

每个变更都会创建完整行和多组 SVG / 按钮，行内再执行 `notes.find()` 与 `trash.some()`；因此标题与回收站匹配最坏为变更数乘笔记数。新建、迁移或大量修改笔记库时，变更数可以接近整个库的笔记数。

实测打开含 **2,003 条未跟踪变更**的 Git 面板，GC 后：

| 指标 | 打开前 | 打开后 |
| --- | ---: | ---: |
| DOM 节点 | 551 | 54,740 |
| 渲染器 JS 堆 | 9.5 MiB | 37.4 MiB |
| DOM 事件监听器计数 | 261 | 8,283 |

这些是挂载完整列表的资源成本，不能直接称为内存泄漏。打开阶段同时等到了后台状态刷新，因此该阶段总耗时不用于声称纯渲染耗时。

建议：为两个变更分组使用虚拟列表；预先构建 filename → title 的 Map 和回收站路径 Set。Git diff 和历史 diff 的逐行渲染也应采用规模限制。

### 6. P2：未指定或不支持的代码语言触发全语言自动识别

位置：[src/codeHighlight.tsx:19](../../src/codeHighlight.tsx#L19)，调用来自 Markdown 预览。

没有受支持语言时直接 `lowlight.highlightAuto(text)`。纯文本代码块样本的自动识别耗时：**16 KiB 为 146.3 ms，64 KiB 为 239.0 ms，256 KiB 为 847.1 ms**。同样内容使用明确的 plaintext 路径均小于 0.1 ms。计算发生在渲染时；多个代码块会叠加，源码预览随内容变更还会再次执行。

建议：未知语言默认按纯文本展示；如果保留自动识别，限制输入长度和候选语言，并在界面线程之外计算。对超大且指定语言的代码块也应设预算。

### 7. P2：空闲轮询与隐藏历史面板仍重复启动 Git 子进程

位置：[src/App.tsx:225](../../src/App.tsx#L225)、[electron/vault.cjs:326](../../electron/vault.cjs#L326)。

打开库后每 5 秒查询状态，每次串行执行 `status`、`rev-list`、`branch`、`remote` 共 4 个 Git 命令。历史 effect 依赖整个 `status` 对象且未检查 `rightOpen`，即使 Git 没有变化、历史面板已收起，也会再次执行 `git log --follow`。

实测空闲 11 秒：大纲状态调用 8 次 Git；先打开历史再收起侧栏，同样 11 秒调用 **10 次 Git，其中 2 次为历史查询**。短样本中的主进程 CPU 分别为 86.5 ms 和 53.6 ms，未见主进程持续高负载；这里确认的是不必要的唤醒与扫描，重仓库下的成本需要另测。轮询也没有在途合并，单次状态查询超过 5 秒时可以重叠。

建议：历史只在可见且 note / HEAD 变化时刷新；相同状态保留对象，避免触发下游更新。状态查询合并在途请求，缓存低频变化的 branch / remote，并在保存、Git 操作与外部文件变化时失效；窗口不可见时降低轮询频率。

## 其他优化空间

- **整库清单写入放大**：[electron/vault.cjs:94](../../electron/vault.cjs#L94) 与第 222 行。三次很短的保存均写入正文和整个清单，共 6 次写入、约 1.20 MiB；该 2,000 篇笔记的清单为 418,741 字节。规模更大、持续编辑时按整个库大小放大。可以独立维护时间索引或批量写元数据，同时保持外部变更检查和持久性语义。
- **富文本和绘图全量序列化**：[src/MarkdownEditor.tsx:282](../../src/MarkdownEditor.tsx#L282) 每次文档变更调用 `getMarkdown()`；[src/Drawing.tsx:42](../../src/Drawing.tsx#L42) 在比较是否变化前就序列化整幅图和附件。源码模式还同步重建 Markdown 预览和字数。可以测量输入长任务后，为预览和统计设置延迟、为绘图先比较持久化状态的版本，并在确保保存 / 导航正确的前提下合并序列化。
- 当前内存脚本中，两轮各 20 次编辑器循环分别耗时 27.5 秒和 81.1 秒。脚本还混合了选笔记、富文本挂载、源码和预览挂载；该差异值得单独做 CPU profile，但本次没有把它归因为某一确定 bug。

## 内存结果及限制

临时修正图片路径断言后，完整脚本通过现有内存断言：初始 RSS 合计 **524.6 MiB**，各阶段最高 **798.7 MiB**，结束 **589.9 MiB**；渲染器结束 GC 后 JS 堆 **18.7 MiB**。搜索堆峰值最高 9.8 MiB；第二轮绘图阶段 GC 后堆增量约 2.24 MiB，低于脚本的 8 MiB 限制。

懒加载编辑器和绘图后，最终堆高于启动堆是本样本的观测结果，不能单凭差值认定泄漏或认定完全无泄漏。已有 Blob URL 撤销、事件监听器清理、搜索取消和侧栏虚拟化均有对应实现，未发现明显缺少清理的固定循环。

8 MiB 图片样本是填充后的 1×1 PNG，只覆盖字节传输，不覆盖高分辨率解码、GIF 动画或大量图片的 GPU 内存。未进行数小时级持续运行、真实大库冷缓存测试或其他操作系统测试。
